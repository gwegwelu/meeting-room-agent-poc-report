會議室預約 Agent 進化紀錄

驗證一件事：人透過平台上的互動，能不能讓初版 agent 進化，而且每次進化都可以檢查、可以追溯。題目與資料全部是模擬的。

題目

為什麼用「會議室預約」來測試

同仁用一句話提出需求，例如「11/3（二）下午要開 2 小時的會，8 個人，需要投影機」。agent 要讀懂需求、查詢預約系統，選出會議室並完成預約，或判斷要轉交給誰。 這個任務人人看得懂、對錯能自動判定，但要做對，得同時處理多重條件、模糊說法、例外情況與過時資料。這些正是「進化」要處理的東西。

適合當測試題目的條件

結果可以客觀評分訂了哪間、幾點，或轉交給誰，和標準答案一比就知道對錯，不必靠人主觀判斷，所以每個版本都能大量重跑。
資料全部可以模擬會議室、行事曆和需求都由程式產生，不碰任何真實資料；也能刻意製造「外觀相似、處理不同」的案件。
四個面向都自然存在有固定步驟（流程）、通用準則（規則）、個案知識（經驗），也有會過時的資料表（既有資產）。
有隱藏的業務慣例真實規則只存在審閱者心中，初版 agent 不知道，只能從人的回饋中學會。

複雜度從哪裡來

多重條件同時成立容量、設備、時段、午休、主辦人行程、樓層要同時滿足，再依「最早、最小」挑一間。
程式與判斷混合最終版流程有 8 個步驟：5 個程式動作、2 個 LLM 判斷、1 個分支。程式和判斷的修改方式與風險不同。
自然語言有歧義「下午」從幾點起算、「貴賓」算不算外賓、「線上加入」和「播放影片」是不是都要視訊。
例外與新類型外賓、視訊連線、個人偏好、大型會議都不在初版涵蓋範圍；其中大型會議還需要動作庫沒有的能力。
資料過時初版的會議室資料表缺了「視訊設備」與「靠窗」，不改資產，規則寫得再對也選不出正確的房間。

初版不知道的 7 條真實規則，各自測什麼

真實規則（只有審閱者知道）初版 agent 的狀況測試的進化類型預期要修改的面向
12–13 點午休，「下午」從 13 點起算詞彙表把「下午」記成 12 點起精進既有資產、規則
人數不能超過容量的八成只看容量夠不夠精進規則

「預期要修改的面向」是設計時的預期；反思器實際改了什麼，記錄在下方的逐回合紀錄中。

案件怎麼分組

和真實任務的對應與差距

結構上和交易監控報告產製相同：固定的處理步驟、必須遵守的準則、累積的個案判斷，以及會更新的名單與範本。

比真實任務簡單的地方：

  • 每件需求只有一句話，沒有長篇文件或多個資料來源。
  • 只有 7 條隱藏規則，正確答案唯一，真實業務常有多個可接受的寫法。
  • 錯誤代價低，不涉及法規責任與多層核准。

所以這次結果證明的是「進化機制」可行，不代表正式任務會一樣順利。

組成

Agent 由「流程程式」和「Skill」組成

流程程式負責能用程式確定做到的事，由 RPA 逐步執行；Skill 是 LLM 在需要判斷的步驟裡參考的知識。進化就是修改這四個面向。

實際內容

agent 每個版本的 Skill 與流程

這就是判斷步驟實際讀到的內容。選擇版本可以看 agent 在那個時間點知道什麼；與前一版相比新增或修改的項目會標出來。

進化機制

人的一次回饋，怎麼變成新版本

反思器可以直接提出修改的，是流程定義和三類 Skill；動作庫只能提出需求，交給人開發。提案必須通過檢查關卡才會升版。

提示詞

模型實際收到的指示

平台裡有兩種 LLM：執行任務的判斷步驟，以及負責提出修改的反思器。兩者都是通用大模型加上固定的指示，沒有另外訓練模型。以下是這次實驗使用的原文。

判斷步驟（執行任務的 agent）

固定的角色說明，加上該版本的規則與經驗。每個步驟另有一段任務指示，輸出必須符合指定的 JSON 格式。


      

      

        
反思器（把回饋變成修改提案）

        
每次被呼叫時，系統提示都相同；使用者訊息則依序放入：目前規格、案件需求、agent 的執行紀錄、實際結果、審閱者回饋，提案被退回時再附上退回原因。每一回合的實際輸入可以在下方逐回合紀錄中展開。

        

        

      

    

  


  

    
可信度

    
只教了幾次，卻自動檢查了上千次

    
進化本身很便宜：人糾正幾次，反思器提幾次修改就完成了。昂貴的是證明這些修改真的有效、而且沒有副作用。每次升版，平台都會把所有測試案件重跑一遍，每件重複多次取平均，避免把運氣當成進步。
